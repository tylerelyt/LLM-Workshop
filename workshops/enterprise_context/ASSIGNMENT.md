# Workshop：给企业知识平台增加项目检索与文档变更订阅

你接手一个已有知识平台。全局检索正常工作，Jira `KNOW-201` 要为 Atlas 项目增加项目检索和文档变更订阅。你的 Harness 已能写复杂程序，这次需要补齐的是项目的业务上下文和团队方法：通过工具读需求、历史评审与现有代码，再决定本次应怎样改。

## 先调查，再形成这次工作的 Spec

可用材料包括当前仓库，以及 MCP 中的 Jira 工单、Wiki 原文与版本、GitLab 文件和历史 MR。页面 `100` 是现状与需求，`101` 是已采用的历史决定，`102` 是当前 SDK 接口。Atlas 与 Borealis 各有一份同名设计文档；标题相同不表示是同一份资料。

请完成 MCP 配置，使 Harness 可以按需取得上述内容；写一份调查 Skill，让下一位同事能够沿团队方法继续工作。Skill 应说明何时使用、怎样调查、如何采用资料，以及怎样检查结果，不必规定唯一的工具调用顺序。

形成 Spec，写清本次目标、采用的资料身份与版本、历史要求、修改范围和验收。实现前能解释至少一条来自历史评审、确实影响本次修改的要求。`shared/wiki_sdk.py` 已被多个调用者使用，本轮保持文件内容不变。

## 现场完成一个可运行的版本

在起始仓库副本中实现：

- 按项目检索，只返回该项目资料；原来的全局检索继续可用。
- 订阅项目文档的业务变化，返回应复核的页面身份和版本；别的项目变化不应混入。
- 同一个变更重复投递时，不重复形成通知；状态保存后换一个应用实例，能够继续处理后续变化。
- 文档项目归属与正文版本独立变化。同一正文版本迁出项目仍需撤出原依据，迁回项目仍需重新纳入。

为了接上独立的行为检查，提供以下外部接口：

```python
app = KnowledgeApplication(sdk)
app.search(query)                       # 保持旧全局行为
app.search(query, project_key="atlas")
state = app.subscribe("atlas")
result = app.poll(state)                # {"notifications": [...], "state": ...}
```

`state` 应能保存成 JSON。通知保留 `page_id`、`version`、`action`；`review` 表示需要复核，`remove` 表示该页面已迁出原项目、需要撤出旧依据。这些是外部验收约定，不限制你的内部结构、算法、函数划分或工具调用次数。

已有功能可用以下命令运行：

```sh
python3 starter/src/application.py --query 检索
```

在副本中修改以后，从 `lab` 目录检查，例如：

```sh
python3 checks/check_lab.py \
  --app runs/my-workspace/src/application.py \
  --out runs/my-workspace-check.json
```

检查器在自己的临时数据中实际修改版本、投递重复事件、保存状态并换实例继续，不修改你的业务数据文件。它检查确定性行为与共享 SDK 内容；Spec、Skill 和资料采用理由仍需要人阅读和讨论。

## 独立追加：文档迁走以后，原项目怎样继续？

发布前出现新变化：Atlas 的设计文档 `100` 从 `v8` 更新到 `v9`，并迁入 Borealis。它的 `page_id` 没变，Atlas 之前采用的 `100@v8` 却已不再属于原项目。Borealis 中原有的同名文档 `200` 也继续更新。后续还可能在正文版本不变时调整项目归属。

请重新调查现状，自己决定要怎样调整 Spec、资料采用范围与应用行为，然后用运行结果说明：

- Atlas 后续检索是否仍混入迁出的页面；
- 已采用的 `100@v8` 怎样被标记需要复核或撤出；
- Borealis 的同名文档变化是否被错误当成 Atlas 的依据；
- 保存过的订阅状态能否正确接上这次变化。

不要跟着讲师的内部步骤复制实现。讨论你的判断、采用的资料和验证方式；如果需要更改公开接口，先在 Spec 中说明兼容安排，再给检查程序提供适配入口。
