# 变更 Spec 模板

标题写明本次需求，文件可按项目已有约定保存，例如 `specs/<工单编号>/spec.md`。如果仓库已有团队模板，优先保持兼容，只补齐本次调查需要说明的内容。

## 目标与现状

用户要完成什么工作？已有系统怎样支持它？目前缺少哪一段能力？用具体对象和可观察结果描述，避免只写“提升效率”。

## 需求与设计依据

| 来源 | 对象与版本 | 与本次变更有关的要求或理由 |
| --- | --- | --- |
| 工单或需求 | 编号、更新时间、地址 | 当前目标与已确认范围 |
| Wiki 或设计 | 页号、版本、地址 | 设计约定和历史采用决定 |
| GitLab | 提交、文件或 MR、地址 | 当前实现、调用者与评审理由 |

只有实际取得并影响判断的资料进入此表。未解决的冲突另行说明，不给猜测补造编号。

## 修改范围与方案

说明本次准备修改的应用、接口、数据或测试；对于有其他调用者的共享组件，依据任务约定说明保持或改变哪些行为。写出选择当前方案的理由，以及需要另行确认的范围变化。

## 验收

把要求写成可以观察的结果，例如“同一关键词在两个项目下返回各自的文档”，并说明怎样从实际调用、事件、版本与回归结果核对。允许不同合理实现，不把文件名、调用次数或某种文字表述当成正确性的唯一依据。

## 实施与下游接力

按当前任务需要列出实施顺序、涉及文件和依赖。测试岗位可补充独立的测试 Spec，与这份需求和设计相互引用；不要用一份 CSV 取代完整规格。
