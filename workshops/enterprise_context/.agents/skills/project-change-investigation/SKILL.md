# 调查清楚，再接着已有系统开发

这项方法服务于存量研发。你已经能够完成复杂实现；真正需要补齐的是本次委托的业务含义、历史决定与可验证的结果。不要只凭仓库和一句需求推测企业上下文，也不要把取到几份资料当成完成调查。

## 先还原这次改动

从用户给出的工单或明确需求开始。通过当前可用的企业工具读取原文，找到关联设计、历史评审和代码位置。先说明这次要解决什么问题，现有系统怎样工作，以及哪些已有要求仍然有效。资料冲突时，比较对象、版本、时间和采用状态，不能把较新的讨论自动当成已采用的设计。

MCP 工具提供资料入口；由你决定当前需要查什么。可以沿工单链接继续读取 Wiki、MR 和源码，不要求每次调用固定数量的工具。记录真正影响方案的来源：工单编号、Wiki 页号与版本、Git 提交或 MR，以及可以回查的地址。

## 把调查结果写成可审阅的 Spec

需要形成变更规格时，按需读取 [Spec 模板](references/change-spec-template.md)。写清目标、现状、仍有效的要求、修改范围、方案和验收办法。模板是帮助下一位同事接着做，不是要求填满无关栏目。

有些工作可以在应用层完成，有些确实需要改共享能力。先依据实际调用关系判断；若方案超出当前已确认范围，说明需要改变什么及其理由，交回范围判断，不能悄悄扩大委托。当前课堂任务对共享 Wiki SDK 的要求，必须从该任务的工单和历史设计中取得，不把它写成所有项目都不能改 SDK 的规则。

只要求调查或规格时，到这里交出完整结果。明确授权实施时，再按照规格修改；用户已经给过实施授权，不必为了同一范围反复询问。

## 实现后，让结果说明完成了什么

先运行已有正常路径，了解当前行为；改动后核对新增行为及受影响的存量调用。验证方法跟随任务：检索要看项目范围与实际文档，文档变更要看事件、页号与版本的关联，代码边界要看真实 diff。不能只检查文件存在或模型说“完成”。

需要组织结果时，按需读取 [验证记录](references/verification-record.md)。记录实际运行命令、观察到的结果、涉及的版本与仍未完成的部分。失败或没有运行的检查如实保留，不把讲师参考实现或准备好的输出称为本次模型运行成果。

提交给下一位同事的内容应包括可继续使用的 Spec、实现差异和运行结果，让他知道做了什么、依据哪一版资料、怎样复核。
